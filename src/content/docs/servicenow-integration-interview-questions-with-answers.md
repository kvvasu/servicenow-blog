Integration interviews are really about failure handling. This page groups the questions by mechanism, and notes the follow-up question that separates memorised answers from working experience.

## ServiceNow Integration Interview Questions with Answers
Integration connects ServiceNow to other systems so records move without manual rekeying. Interviewers ask about the platform because most build work depends on it. You must know outbound calls, inbound REST endpoints, and the MID Server. Expect questions on REST versus SOAP, Table API versus Scripted REST API, and how to keep credentials out of scripts. Wrong choices surface later as timeouts, duplicate records, and unsupported customisations, so explain the trade-off behind each answer.

### Core Concepts & Architecture (1–10)
### 1. What are the different types of integrations supported by ServiceNow?
ServiceNow supports several integration patterns. Outbound integrations call a third-party REST or SOAP endpoint from Script Includes, Scripted REST APIs, or IntegrationHub actions. Inbound integration exposes platform data through the Table API, Import Sets, or a custom Scripted REST API. Other routes include JDBC through a MID Server, Email Inbound, LDAP, and the ServiceNow Store. Interviewers probe the failure mode: calling external services synchronously inside a business rule blocks the user transaction and burns a thread.
### Introduction
Picking an integration pattern early saves rework later. Each option carries a cost in licensing, maintenance, and debugging time, and the cheapest to build is rarely the cheapest to run. An admin should match the pattern to the data volume, the latency the business tolerates, and who owns the remote system. When teams skip this step they rebuild the same connector three times and inherit silent failures that only appear under load.
### A. Web Service Integrations
Web services dominate because every vendor speaks HTTP now. ServiceNow calls out with RESTMessageV2 or SOAPMessageV2, and receives with the Table API or a Scripted REST API. Text-based payloads make debugging straightforward and keep the contract versionable. The trap is treating calling code as synchronous. A RESTMessageV2 call inside a before business rule delays the commit and can time out. Move outbound calls to Flow Designer, a scheduled job, or an event queue.
#### A1. Usage of an ESB or Integration Middleware
An ESB or middleware sits between ServiceNow and many back-end systems. It centralises mapping, retries, and protocol translation, so ServiceNow speaks one contract instead of five. That centralisation costs money, adds a hop, and moves integration uptime into another team's hands. Interviewers like this answer when the candidate names the trade-off. An ESB protects the instance from churn, but it becomes a single point of failure and a queue nobody monitors.
#### A2. ServiceNow Instance Integration Options
For instance‑to‑instance integration, consider the following:
#### Service Bridge
Service Bridge connects a provider instance to customer instances in telecom, tech, and MSP scenarios. The provider pushes tasks, cases, and updates into the customer instance without exposing raw tables. Customers control what the provider sees through configured filters and shared fields. The failure mode interviewers watch for: teams treat it as a general-purpose REST channel. Service Bridge expects provider-consumer roles, so using it for peer-to-peer sync produces authorisation errors and records that land in the wrong domain.
#### Instance Data Replication (IDR)
Instance Data Replication copies records from one instance to many, or bidirectionally, so large shared sets stay close to real time. It works at the table level with defined replication sets rather than scripted calls. Candidates should note the cost: IDR consumes network bandwidth and storage on both sides, and bidirectional sets invite update loops. A loop overwrites the newer record with stale data, and nobody notices until an audit. Conflict rules and a clear system of record prevent that.
#### Remote Process Sync (RPS)
Remote Process Sync keeps a flow running across two instances. A playbook defined on one instance drives work on the other, and RPS orders messages so steps execute in sequence. It suits long-running processes such as order fulfilment split between provider and customer. The risk sits in version drift: change the flow on one side without publishing to the other and messages fail validation. Teams then see a stalled process with no obvious error on the remote instance.
#### Remote Instance Spoke
The Remote Instance Spoke ships actions that call another ServiceNow instance from Flow Designer, covering record create, update, and query. It suits occasional or ad hoc calls because configuring it takes minutes. It scales poorly. Each action opens a fresh outbound call, so a flow looping over thousands of records exhausts transaction quota and hits REST limits. Interviewers expect the candidate to say when to move up: steady high-volume traffic belongs on Instance Data Replication or a purpose-built endpoint.
#### A3. Using an Out‑of‑the‑Box (OOTB) Solution
#### Native Integration (Plugin or Store App)
Vendors publish native integrations as plugins or Store apps, such as the HR integrations that link ServiceNow to an HCM system. They ship tested mappings, scheduled jobs, and spoke actions. Buying beats building, because the vendor maintains the connector against API changes and the support contract covers breakage. The candidate should ask about plugin version compatibility. A Store app that lags behind the platform release forces an upgrade stall. Teams discover that stall only when the instance is already locked to an old version.
#### IntegrationHub Spokes
Spokes package low-code actions that call a third party API from a flow. An admin drops an action into Flow Designer, configures a connection and credential alias, and the spoke handles authentication and pagination. Building the same call by hand means writing a REST step, parsing the response, and handling errors yourself. Spokes shine for moderate volume. They slow down long loops though, because each action runs a round trip and the flow engine caps how many steps one transaction executes.
#### Extending a Spoke with Spoke Generator
Spoke Generator reads an OpenAPI specification and generates spoke actions, so a team models a third-party API without writing each action. It creates the action shell, input and output variables, and the request mapping. The generated code still needs review: naming conventions, error handling, and pagination rarely match the API quirks. Candidates who claim it removes all work miss the point. Skipping review ships actions that swallow error responses and return empty outputs, which makes a downstream flow look like it succeeded.
#### Technology Partner Store Apps
The ServiceNow Store lists partner-built integration apps that target common systems. Before a team writes a custom connector, checking the Store costs one search and maybe a licence fee. Partner apps carry support, upgrade paths, and certification against current platform releases. The catch: they solve the generic problem, not your edge cases, and a licence per integration adds recurring cost. Candidates should frame the decision as build cost plus maintenance against licence cost plus limited flexibility.
#### A4 & A5. Initiating System and Pull vs Push
#### Initiating System
The initiating system is whoever starts the conversation. When ServiceNow calls out, an outbound REST or SOAP message leaves the instance, and the remote system receives it. When a third party calls in, the request hits the Table API or a Scripted REST API and lands as an inbound transaction. The label matters because it decides where authentication lives and which side owns retries. Teams that leave retry logic to nobody lose records when the far end is briefly unavailable.
#### Pull vs Push
Pull means ServiceNow asks for data, usually through a scheduled job running a RESTMessageV2 call or an Import Set. Push means the other system sends data in, either by calling a Scripted REST API or by publishing to a queue. Pull suits batch reconciliation and gives the instance control over timing. Push delivers lower latency but leaves the instance exposed to whatever volume the sender produces. Interviewers want to hear that choice tied to volume, latency, and who owns the retry path.
#### A6. Process (REST) APIs
Process APIs expose a specific workflow rather than a table. The Catalog API, for example, takes a structured payload with item variables and enforces catalog rules. Change and Incident Process APIs behave the same way. They validate more than a generic table insert, which keeps data clean. They also bypass some business rules and ACL behaviour a developer expects. Calling a Process API without the exact schema returns a validation error, and a retry cannot repair the payload.
#### A7. Choice of Web Service Protocol
REST is the default choice today. JSON payloads stay readable, HTTP tooling makes debugging simple, and the Table API and Scripted REST API both speak it natively. SOAP still appears where a legacy system publishes a WSDL and cannot change, and inbound SOAP needs a Scripted Web Service instead. Interviewers press on the reasoning, not the preference. A team that picks SOAP for new work inherits heavier payloads and weaker tooling support, so the choice needs a concrete constraint behind it.
#### A8. Table API vs Scripted REST API
The Table API works against any table with no setup, and ServiceNow generates the endpoint automatically. Developers get CRUD plus query parameters such as sysparm_query and sysparm_fields. A Scripted REST API gives full control: custom paths, custom payloads, and logic that spans several tables. Interviewers test judgement here. Expose a raw table that holds sensitive fields and ACLs become the only guard. Write a Scripted REST API when the caller needs a shape the table does not provide.
### B. Persist Data in ServiceNow
Not every integration should store what it fetches. Some teams keep data in the source system because of licence cost, data residency rules, or sheer volume. Others store it because reporting, ACLs, and workflows only work on platform tables. Persisting brings consequences: storage cost, stale copies, and a second place to reconcile after the source changes. An interviewer listens for whether the candidate names who owns the truth when both systems hold the same record.
#### B1. Data Sources supported by Zero Copy Connectors
Zero Copy Connectors expose external data as Data Fabric tables without copying rows into the instance. The connector queries the source at read time, so workflows and reports see current values. Supported sources include cloud data warehouses, databases, and external object stores. The trade-off is latency and dependence. Every read travels to the source, so remote availability and the network path become part of your user experience. Cached copies help, but they bring back the staleness the design set out to avoid.
### C. Event‑Driven Architecture (EDA)
Event-driven architecture flips the model from request and response to publish and subscribe. ServiceNow produces events to a message broker, and consumers act on them when they can. Nothing blocks the producer transaction, so a slow consumer cannot stall the platform. The cost sits in debugging, because failures happen somewhere else and arrive later. Interviewers want a candidate who names ordering, duplicate delivery, and poison messages as design concerns. At-least-once delivery means the consumer must handle the same event twice.
#### C1. Direction of Data Flow
Direction decides the plumbing. Producing means ServiceNow publishes to a broker such as Kafka and external systems subscribe, using the Streaming API and a configured topic. Consuming means the instance reads from a topic and reacts, often through a Kafka Message trigger in a flow. Mixing both directions on one topic creates a feedback loop where the instance consumes an event it produced and re-publishes it. Teams must set the topic and partition strategy deliberately.
#### C2. Consuming External Data
The Kafka Message trigger starts a flow when an event lands on a subscribed topic. The flow then parses the payload and writes platform records, or calls another system. Because triggers run per message, a burst of events can spawn many flow executions and exhaust the transaction quota. Consumers need idempotency. A retried message that creates a second incident for the same problem looks like a platform bug to the user. Store a correlation key and check it before creating anything.
#### C3. Streaming ServiceNow Data
Streaming pushes platform records outward. The Streaming API publishes events such as record inserts and updates to an external broker. Log Export Service streams logs and audit data without custom scripting, and it suits security monitoring and long-term retention. Teams should size the broker and the retention policy before they turn it on. The instance does not buffer events for a consumer that is down. Events produced while the broker is unreachable are gone, not queued.
### D. AI Agents
AI agents on the Now Platform reason over a task and choose tools to finish it, which lets one request touch several systems. That flexibility costs predictability. An agent picks an action from a description, so two runs of the same request can take different paths and produce different rows. Interviewers ask where agents fit in an integration. Use them for triage, summarisation, and routing, and keep record writes behind deterministic APIs with validation and audit.
#### D1. A Deterministic Web Service might be the Better Choice
When the requirement is stable and auditable, a REST API beats an agent. A REST contract declares its schema, returns the same shape every call, and fails with a status code a developer can test. An agent decides at runtime, which makes results hard to reproduce and harder to defend in an audit. Reach for AI where the input is unstructured or the routing rule keeps changing. Put the actual record writes behind the deterministic endpoint either way.
#### D2. MCP vs A2A
Model Context Protocol lets an agent discover and invoke tools from a server over a standard interface. Agent2Agent instead lets two independent agents negotiate tasks and exchange context as peers. Choose MCP when one orchestrator needs many capabilities and you control the tool server. Choose A2A when separate systems own their own reasoning and must delegate work across trust boundaries. Interviewers probe what happens when a spoke exposes tools without scoping: the agent calls everything it discovers, including write actions nobody intended.
#### D3. When to Use an Agentic Spoke as an Agent vs Add a Tool
An Agentic Spoke already wraps a vendor API as agent-callable tools, so the platform maintains the schema and authentication. Adding a tool means you keep the endpoint, headers, and payload mapping yourself. Pick the spoke when it covers the operation. Build a custom tool only for gaps the spoke cannot reach. Interviewers chase one failure mode. Teams add a raw tool beside the spoke, so the agent gets two paths to the same record and writes twice.
### E. UI‑level Integrations
#### E1. CRM Components
Customer Service Management draws on Engagement Messenger for web chat, while Adobe Experience Manager handles CMS-driven portals. Both push interactions into the same case tables. The interview point is where conversation data lands: if the component bypasses the case model, agents lose context and reporting splits. Confirm which component owns the authenticated session before wiring anything.
#### E2. UI Integration within a Mobile App
The Mobile SDK embeds ServiceNow data and functions inside native iOS and Android apps. Clients fetch records through the SDK rather than the browser, so calls still respect ACLs and the logged-in user's roles. The trap: developers cache responses locally for offline use, then replay stale data after a role change. Session handling also breaks when the host app refreshes tokens on its own schedule.
#### E3. iFrame
An iFrame renders an external page inside a ServiceNow UI page or dashboard. Same-origin rules block the parent from reading the child DOM, so passing state needs postMessage or query parameters. Cross-site scripting protections and third-party cookie policies often break the embed outright. Interviewers expect you to name the real risk. An untrusted frame can phish a logged-in agent, and X-Frame-Options on the remote server stops the embed entirely.
### F. Fallback Solutions
File-based transfers, RPA, and email survive as fallbacks when no API exists. Each one loses something. Flat files arrive without schema enforcement, so bad rows land silently. RPA drives a UI and breaks whenever a button moves. Email carries no delivery guarantee and no structured payload. Use them as bridges with a retirement date, never as the target architecture, and say why the real endpoint is missing.
### 2. What is the difference between REST and SOAP integrations in ServiceNow?
RESTMessageV2 sends JSON or XML over HTTP verbs, and SOAPMessageV2 wraps requests in an envelope with a WSDL contract. REST suits lightweight, stateless calls and fits ServiceNow's own Table API. SOAP wins when the partner publishes a rigid WSDL and enforces WS-Security. The failure interviewers look for: developers parse SOAP responses with string functions instead of the response object, so a namespace change silently returns empty values.
### 3. What is IntegrationHub and why should we use it?
IntegrationHub runs actions and subflows on the Flow Designer engine, with spokes supplying prebuilt steps and connection credentials stored centrally. It moves integration logic out of Business Rules, where developers previously hand-rolled every HTTP call. The cost is licensing and the action execution quota, consumed per run. Interviewers probe what happens when a flow calls an action inside a loop: the quota drains fast and the transaction slows.
### 4. How do you secure REST integrations in ServiceNow?
Outbound calls authenticate through a Connection and Credential alias, so passwords never sit in scripts. OAuth 2.0 flows, mutual TLS, and basic auth all configure there. Inbound calls authenticate against a dedicated integration user. The mechanism matters less than the boundaries: give that user only the roles the endpoint needs. Interviewers ask about ACL enforcement because a REST call runs as its authenticated user, and over-broad roles expose every table the integration touches.
### 5. What is the role of a MID Server in integrations?
A MID Server runs inside the customer network and polls the instance for work, so ServiceNow never opens an inbound firewall port. It executes probes, REST calls, and PowerShell against on-premise systems, then posts results back through the ECC Queue. Credentials live on the MID Server, encrypted with the instance key. The failure mode: teams deploy one MID Server for everything, and a single overloaded node stalls discovery, orchestration, and integration at once.
### 6. What are Scripted REST APIs in ServiceNow?
A Scripted REST API groups resources under your own URI, and each resource handles a method with server-side JavaScript. Developers reach for it when the Table API cannot express the operation, for example a multi-table transaction or a custom response shape. The endpoint still runs as its authenticated caller, so ACLs and the integration user's roles decide what returns. Interviewers probe error handling: an uncaught exception returns a generic 500 and leaks no useful diagnostic.
### 7. What are the steps to create a REST integration in ServiceNow?
Define a REST Message record, add HTTP methods with their endpoints and headers, then set authentication through a Connection and Credential alias. Test each method in the REST API Explorer before calling it. Invoke the message from a Business Rule, a Flow Designer action, or a scheduled job. The step teams skip is error handling: RESTMessageV2 returns a response object rather than throwing, so code that ignores the status code records false success.
### 8. What are Transform Maps and when do you use them in integrations?
A Transform Map converts staging rows from an import set into target table records. Field maps define matching, coalescing, and data transformation, while onBefore or onAfter scripts handle logic the maps cannot express. Integrations route external payloads through import sets when they need deduplication against existing records. The failure mode: no coalesce field means every load inserts duplicates, and the table grows silently until reports double-count everything.
### 9. What is OAuth and how is it used in ServiceNow integrations?
OAuth issues a short-lived access token after the client proves its identity, so ServiceNow holds a token instead of a stored password. The instance registers as a client through an OAuth application registry, and REST calls attach the bearer token. Refresh tokens extend the session without re-authentication. Interviewers probe token expiry: when the refresh fails and code swallows the error, every downstream call returns 401 and the integration dies quietly.
### 10. What is a spoke in IntegrationHub?
A spoke packages related IntegrationHub actions, subflows, connection definitions, and often an OAuth registry entry for one external system. Installing a spoke gives flows tested, vendor-maintained steps instead of custom HTTP code. Actions extend a base class and expose typed inputs and outputs. The trap: teams install a spoke for a single action and inherit upgrade overhead for the whole package.
### Inbound Integrations (11–20)
### 11. How do you expose a ServiceNow table via REST API?
The Table API exposes any table over REST once the caller holds read access and the table allows it. Requests hit /api/now/table/{table} and support filters, field selection, and pagination through sysparm_query, sysparm_fields, and sysparm_limit. ACLs still run for the authenticated user. The interview point: developers assume the API ignores ACLs, then wonder why a call returns an empty result set instead of an error.
### 12. What is the purpose of REST API Explorer in ServiceNow?
The REST API Explorer lists every REST service the instance exposes, including Scripted REST APIs, and generates ready-to-run requests. It shows required headers, path parameters, and the authentication the endpoint expects. Developers use it to isolate whether a failure sits in ServiceNow or the calling system. Interviewers probe its limits: the Explorer runs as the logged-in user, so a successful test says nothing about whether the integration user's roles will pass.
### 13. How do you handle authentication in inbound REST calls?
Inbound callers authenticate through basic auth, OAuth, or mutual TLS, and ServiceNow runs the endpoint as the resolved user. A dedicated integration user with narrowly scoped roles limits blast radius. Store credentials in the calling system's vault, not in scripts or workflow fields. The failure interviewers expect: teams reuse an admin account for convenience, so a leaked credential exposes the whole instance instead of one table's records.
### 14. What is a Scripted REST Resource and why is it needed?
A Scripted REST resource defines how one URI path responds to a given HTTP method. The script reads request body and query parameters, performs work through GlideRecord or a script include, then sets the response status and body. Resources organize under a parent API and inherit its security. Interviewers probe whether the developer sets an explicit status code and Content-Type, because defaults mislead callers about what actually happened.
### 15. How do you validate input data in Scripted REST API?
A Scripted REST resource validates input by inspecting request.body.data and request.queryParams before touching any table. Check required fields, types, allowed values, and string length, then set an explicit 400 response with a message naming the bad field. Reject early rather than letting GlideRecord insert malformed rows. Interviewers probe whether validation trusts client-supplied sys_id values, because an unvalidated reference can link a record to a table the caller should never reach.
### 16. What is the role of ECC Queue in integrations?
The ECC Queue, table ecc_queue, carries asynchronous messages between the instance and MID Servers. The instance writes an output record, a MID Server picks it up, executes the work, then writes an input record with the result. This design lets the MID Server poll outbound, so no inbound firewall rules are needed. Interviewers probe stuck work: if a MID Server dies mid-job, the output record never resolves on its own.
### 17. How can you log integration requests and responses?
Log integration traffic with gs.info and gs.error in the source. When you need queryable history, write structured rows to a custom log table. Include the endpoint, correlation ID, status code, and payload size. Never log credentials, tokens, or full PII payloads. Interviewers probe transaction detail. gs.log output lands in the node logs and rotates quickly. Teams that rely on it alone lose the evidence they need when an integration fails overnight.
### 18. What are Subflows and Actions in IntegrationHub?
Actions perform one task, such as a REST call or script step, and expose typed inputs and outputs. Subflows chain actions with branching and error handling, and a flow calls them like any other step. This split lets teams reuse logic across flows without copying it. Interviewers probe scope. An action runs with the flow's user context. Credentials and ACLs inherited from the caller can fail when a different flow triggers the same subflow.
### 19. What are best practices for building scalable inbound integrations?
Accept the request fast, then process asynchronously. Write a staging record or fire a business rule that queues an event, and let a scheduled job or event handler do the heavy work. Cache reference data instead of querying per call, index the fields you filter on, and cap payload size. Interviewers probe the synchronous trap: a caller waiting on a multi-table transaction hits the transaction quota and times out, and retries then duplicate records.
### 20. How do you test inbound REST APIs?
Test with Postman or the REST API Explorer to confirm authentication, headers, and payload shape. Then build negative cases: missing fields, wrong types, oversized payloads, expired tokens, and a caller lacking the required role. Assert on status codes and the record state afterward, not just the response body. Interviewers probe regression coverage because a passing happy-path call proves nothing about how the endpoint handles bad input.
### Outbound Integrations (21–30)
### 21. How do you send data to an external system using REST?
Build a RESTMessageV2 object, set the endpoint and method, add headers and authentication, then attach the payload through setStringParameter or setRequestBody. Call execute() and read the response object for status and body. Check the status code before treating the call as successful. Interviewers probe retries: a naive retry loop after a timeout can create duplicate records on the remote system unless the payload carries an idempotency key.
### 22. What is the difference between synchronous and asynchronous outbound REST calls?
A synchronous call blocks the thread until the remote endpoint replies. The script that calls RESTMessageV2.execute() waits, so any Business Rule or UI Action holding that transaction stays open too. Long waits exhaust worker threads and can hit the transaction quota, leaving users on a spinner. An asynchronous call returns immediately; the response lands later, so the script cannot read the return value inline and must check the outbound log instead.
### 23. What are common HTTP status codes in REST integrations?
-   200:  OK
-   201:  Created
-   400:  Bad Request
-   401:  Unauthorized
-   404:  Not Found
-   500:  Server Error
### 24. How do you handle errors in RESTMessageV2?
A RESTMessageV2 call does not throw when the remote server returns an HTTP error. The script still gets a response object, so an admin must read getStatusCode() and branch on it. Wrap the call in try/catch for transport failures, then inspect the status code and getErrorMessage(). Teams that only catch exceptions treat a 500 or 401 as success, write bad data, and leave the retry logic untouched.
### 25. How can you prevent duplicate data during integration?
Give every inbound record a key the source system controls, then make ServiceNow coalesce on it. An Import Set transform can coalesce on that external ID instead of sys_id. Store the key in a field and back it with a unique index, so a duplicate insert fails loudly rather than silently. Teams that coalesce only on short description or caller create a new incident on every retry, and the help desk merges tickets for weeks.
### 26. What’s the use of Import Set API in integrations?
The Import Set API exposes a staging table over REST at /api/now/import/{table_name}. An external system posts an array of records, ServiceNow writes them straight into staging, then runs the transform map you attached to that table. Because the transform runs inline, the caller gets per-record results showing which rows inserted or failed. Large payloads can exceed size limits, and one bad row does not roll back the rest, so partial loads need their own reconciliation.
### 27. How do you pass dynamic parameters in RESTMessageV2?
Define variables in the REST Message record as ${name} placeholders, then fill them at runtime with setStringParameter(). That method URL-encodes the value, which corrupts JSON bodies and query strings that need raw characters. setStringParameterNoEscape() writes the value untouched, so a developer uses it for body fragments and pairs it with proper escaping. Building the whole payload through string concatenation instead breaks on quotes, and one stray ampersand splits a query parameter.
### 28. What is the Table API vs Aggregate API vs Attachment API?
The Table API at /api/now/table reads and writes full records. The Aggregate API at /api/now/stats returns counts, sums, averages and group-by results without sending record data. The Attachment API at /api/now/attachment uploads and downloads files. Use stats when the caller only needs numbers, because paging thousands of table rows to count them burns REST quota and slows the response. Note that aggregate results honour ACLs differently, so a user can see a count they cannot read record by record.
### 29. How do you transfer attachments in integration?
Post the file to /api/now/attachment with table_name, table_sys_id and the file content. The instance stores it against the target record. The download direction uses GET /api/now/attachment/{sys_id}/file, which streams the bytes back. Embedding a binary inside a JSON body forces base64 encoding. That encoding inflates the payload and can cross request size limits. Large transfers routed through a MID Server avoid instance memory pressure, and the integration user needs write access to sys_attachment.
### 30. How can you monitor failed integrations?
Check the Outbound HTTP Requests table, where every RESTMessageV2 call logs its endpoint, status code and response body. The ECC Queue holds work the MID Server has not yet hauled back, so stuck or errored probes show up there. Flow executions record each IntegrationHub action and its failure reason. These tables stay empty only if the integration never runs. A report that counts rows per hour exposes a dead feed faster than a dashboard of green ticks.
### Real-time Scenarios & Troubleshooting (31–40)
### 31. How would you integrate Jira with ServiceNow?
Two directions matter. Outbound, a spoke or custom RESTMessageV2 creates and updates Jira issues over its REST API. Inbound, a Scripted REST API receives Jira webhooks and maps fields onto ServiceNow records. Keep a cross-reference table holding each Jira key and its ServiceNow sys_id. The classic failure is a feedback loop. A status change fires an update into Jira, Jira echoes the change back, and both records flap until someone disables the business rule at midnight.
### 32. Why is my REST call returning 401 Unauthorized?
A 401 means the instance rejected the credentials before it ran any record query. Common causes: the integration user lacks the web service access only role. The credential record may hold a stale password, or the Authorization header never reached the endpoint. A 403 works differently and points at ACLs instead. An admin checks sys_user for an active account and confirms the endpoint REST API access. A disabled user returns 401 even when the password is correct.
### 33. What is a webhook and how do you consume it in ServiceNow?
A webhook is an HTTP POST that an external system fires when something happens, rather than ServiceNow polling for news. To consume one, build a Scripted REST API resource and hand the external system its URL. Authenticate the caller with a shared secret, a signature header, or an OAuth profile, and validate the payload before writing anything. Public webhook URLs that skip authentication let anyone create records, and a missed signature check turns every POST into a forgery risk.
### 34. How do you handle retries in failed outbound integrations?
Log every outbound attempt in a custom table with a status and a retry count, then let a scheduled job pick up the failures. Retry only transient errors such as timeouts and 5xx responses; a 400 or 401 will fail identically forever. Space attempts apart with increasing delay so a dead endpoint recovers instead of drowning. Combine retries with an idempotency key, otherwise the second attempt creates a duplicate record on the remote system.
### 35. How do you manage long-running integrations?
Push the work off the user's transaction. An outbound REST call inside a synchronous Business Rule holds the thread until it returns, and ServiceNow cancels transactions that run too long. Use executeAsync(), an event the system queues for later, or a Flow Designer action that runs asynchronously. Chunk big batches across scheduled jobs that checkpoint progress, so a cancelled run resumes from the last processed record instead of starting over.
### 36. How do you prevent overloading external APIs?
Pace the calls. Queue outbound work in a table and let a scheduled job send a controlled number per interval. Do not fire hundreds at once from a Business Rule. Watch for 429 responses and back off when they appear, since hammering a throttled API only extends the outage. Cap how many async calls run at the same time. Most overload stories start with a loop that calls an external API once per record on a large query.
### 37. How to secure sensitive data in integration scripts?
Store secrets in the Credentials table and reference them through a Connection and Credential alias, so scripts never hold a literal password. The outbound REST step then pulls the credential at run time and the value stays encrypted at rest. Hardcoding keys inside a Script Include leaks them to every admin who reads that record, and to anyone with a cloned instance. Also scrub response bodies before logging, since tokens often appear in error text.
### 38. How do you track integration transactions?
Write one row per attempt into a custom log table holding the correlation ID, endpoint, request payload, response, status code, timestamp and retry count. That correlation ID is what lets an admin tie a single business transaction across systems when a record never arrives. Store the payload carefully and trim large bodies, because that table grows fast and an unarchived log slows every query. A scheduled cleanup job keeps it manageable.
### 39. How do you integrate ServiceNow with Microsoft Teams or Slack?
Use the IntegrationHub spoke for the target product, because it handles authentication, message formatting and the API calls the platform exposes. For simple notifications, an admin can post to an incoming webhook URL that the channel generates. The spoke route keeps credentials in the alias and survives token rotation. Simpler webhook approaches fail when the token expires or when the channel owner leaves, and nobody notices until notifications stop for a week.
### 40. How do you debug a failed REST call?
Reproduce the call in a background script and read getStatusCode(), getErrorMessage() and getBody() before you assume anything. The Outbound HTTP Requests log keeps the exact endpoint, headers and response the instance sent. That record shows whether the failure sits in your payload or the remote service. An empty body usually means the remote returned HTML or the request never left. Check ACLs and the endpoint URL last, after the response tells you what happened.
### Advanced & Best Practices (41–50)
### 41. What are the best practices for API versioning in Scripted APIs?
-  Use versioned URIs (e.g., /api/x_app/v1/resource).
-  Deprecate older versions gracefully with notification.
### 42. How do you schedule integration runs in ServiceNow?
A Scheduled Script Execution runs a script on a cadence as a chosen user, and a scheduled flow trigger does the same for Flow Designer. Both run as that user, so ACLs and the integration account's roles decide what the job can read. Guard against overlap: a job that needs twenty minutes but fires every ten stacks copies of itself, and each copy processes the same records. Track a last-run timestamp and skip records already handled.
### 43. How do you bulk integrate data from another tool?
Load the source rows into a staging table first, then let a transform map move them into the target. Data sources handle REST, JDBC, LDAP and flat files, and the transform engine gives each row coalesce rules and field mappings. Run large loads in chunks through scheduled jobs, because one long-running import can exceed transaction limits and leave staging half converted. Coalesce on the external key so a rerun updates instead of duplicating.
### 44. What is the best way to test integrations in lower environments?
-  Use sandbox/test accounts with limited permissions.
### 45. Can ServiceNow call external APIs without coding?
Yes, Flow Designer with IntegrationHub handles many outbound calls without a line of script. A spoke ships predefined actions, and the generic REST step lets an admin set the endpoint, headers and body as form fields. The limits matter: a spoke only covers the API operations its author built, and anything unusual needs a custom action or a script step. Complex authentication and payload shaping often push the work back to a developer.
### 46. How do you handle data transformation in integrations?
Transform the payload before it reaches the target table, so downstream business rules and notifications see clean values. An Import Set transform map handles inbound rows through field mappings plus onBefore and onAfter scripts. Date formats, code lookups and reference resolution belong there. Outbound flows use a script action or a reusable Script Include, so two integrations share one mapping. Transforming inline in the destination leaves no staging copy, so a bad conversion is hard to trace or rerun.
### 47. How can you integrate ServiceNow with legacy systems with no API support?
When a system offers no API, reach it through its database or its file system. A JDBC data source driven by a MID Server queries the legacy database directly. An SFTP file data source reads exported flat files into a staging table for a transform map. Email remains a fallback for systems that only send messages. Each path carries risk: a schema change breaks a JDBC query silently, and a malformed file fails mid-load without a signal.
### 48. What’s the role of Scoped Apps in integrations?
-  Encapsulate logic for reuse and distribution.
-  Maintain version control and permission isolation.
### 49. What are best practices for integration documentation?
Document the contract, not the code. Record the endpoint, HTTP method, authentication type, request and response schemas, and the field mapping between systems. Add the error codes you expect and what each one triggers, plus the retry policy and the owning team. Keep it next to the integration record rather than in a wiki nobody updates. Undocumented integrations become black boxes, and the first person asked to fix one after a handover spends days tracing calls.
### 50. How do you monitor and alert integration failures in production?
Alert on the integration log table, not on a dashboard nobody opens. A scheduled job scans for failed rows in the last interval and raises an event or sends a notification to the support group. Event Management can ingest those events, correlate them and open an incident automatically. Add a heartbeat check for silent feeds, because the dangerous failure produces no rows at all. Alert thresholds set too tight bury the real outage.
