Release names come and go faster than the platform's underlying ideas. This page traces the shift from workflow automation to the AI platform, so a feature you meet today has a visible lineage.

## A History of ServiceNow Releases: From Workflow to AI
ServiceNow began as an IT service management platform that automated help desk tickets. Each release family added depth: workflow engines, a portal, a service catalogue, and later a scripting model that let developers extend the core. Over time the product moved from internal workflow toward enterprise-wide service delivery. Recent families push machine learning and AI agents into resolution and routing. This history traces how each generation changed the way administrators and developers work.
### 1. The Early Days: The "Seasons" Era (2004–2011)
This era covers the years before the alphabetical names that most admins recognize. ServiceNow ran as a hosted service delivering IT help desk workflows without on-premise installs. Early versions carried season names, so teams referred to Winter or Fall builds rather than a marketing label. That habit caused confusion, because two customers could run different builds under the same season name. Support engineers had to confirm an exact patch level before suggesting a fix.
### 2. The Alphabetical Pivot: Aspen to Fuji (2011–2015)
A switch to alphabetical city names gave every release a stable, ordered identity. Customers could finally compare notes, and upgrade planning became simpler because the sequence itself carried meaning. The platform also widened its scope in these years, moving past core incident and change management into broader application modules. Each release shipped new tables and properties, so an admin who skipped documentation risked activating behaviour that a later upgrade assumed. Naming discipline made those jumps survivable.
### 3. The Enterprise Expansion: Geneva to Quebec (2015–2021)
This stretch pushed the platform far past IT service management. Human resources, security operations, customer service, and governance products arrived, each with its own tables and roles. That expansion changed how admins work, because a change in a shared table can break an unrelated application. It also made scoping and domain separation essential, and many organisations learned that lesson the hard way when a report exposed data across business units.
### 4. The "Next Experience" & AI Era (2022–Present)
Recent releases reworked the user interface and pushed automation into the Flow engine. The platform now hosts workspaces, UI Builder pages, and a unified navigation that replaced the classic header. Predictive intelligence and virtual agent features arrived alongside, and later releases folded generative AI into the same surface. Admins faced real work in this period. Every legacy client script and portal widget needed review. The new experience renders data through different components and resources.
### 5. The 2026 Strategic Shift (The "Australia" Release)
After Zurich, the city sequence wrapped back to A. The Australia family continues that pattern, and the company has adjusted how often major releases land. Fewer, larger upgrades change the planning math: a skip now carries more risk, and testing windows stretch further. Admins should confirm the current schedule on the official release page rather than a blog post. Map each skipped release note against the instance before booking the upgrade.
